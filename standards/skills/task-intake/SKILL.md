# 착수 문답 절차 (task-intake) v1.3

목적: **처음에 집요하게 한 번 묻고, 그 뒤로는 막힘없이 끝까지 간다.** 재작업 한 판은 착수 문답 수십 번보다 비싸다(원장 §0-1: 판 하나를 다시 돌리면 약 100만 토큰).

## 원칙 5개

1. **묻기 전에 찾는다.** 파일·Drive·전회차 폴더·스킬·표준에서 확인할 수 있는 것은 묻지 않고 「확인한 사실」로 제시한다(FB-53, FB-01).
2. **결과를 바꾸는 것만 묻는다.** 질문마다 「답에 따라 무엇이 달라지는가」를 속으로 확인하고, 달라지는 것이 없으면 뺀다.
3. **한 번에 모두 묻는다.** 질문을 쪼개 여러 턴에 걸쳐 묻지 않는다. 모든 질문에 추천 기본값을 달아 「나머지 기본값」 한 마디로 답할 수 있게 한다.
4. **이해를 문서로 확인받는다.** 답을 받으면 작업 명세서 1장을 내고 승인을 한 번 받는다. 승인 뒤에는 명세서가 기준이다.
5. **실행 중에는 멈추지 않는다.** 새 의문이 생기면 가정을 기록하고 진행한다. 멈추는 것은 비가역 작업, 과업의 핵심·프레임 변경, 명세서와 정면 충돌하는 사실이 나왔을 때뿐이다.

## 단계

### 1단계 · 자체 탐색 (질문 전, 사용자에게 보이지 않게)

- Drive `/_피드백백로그/ACTIVE_RULES.md`와 해당 도메인 표준(제안서는 `PROPOSAL_STANDARD.md`)을 읽는다. `BACKLOG.md` 전문은 읽지 않는다.
- 첨부 파일, 같은 과업 폴더, 전회차 폴더(`01_제안서/<연도>/` 등), 정본·템플릿을 찾는다.
- 큰 파일(10만 자 이상)은 대화에 올리지 않는다. 디스크에 저장하고 스크립트로 필요한 부분만 뽑는다.
- 여러 폴더를 훑어야 하면 탐색 전용 서브에이전트에 맡기고 결론만 받는다.

### 2단계 · 질문 배치 (한 번)

아래 형식으로 **한 메시지에** 낸다.

```
[확인한 사실] (찾아서 확정한 것 — 틀렸으면 지적만 해 주시면 됩니다)
- 기준 자산: …(경로) / 입력 자료: …(최신본 판단 근거) / 마감: …(출처)

[질문] 번호: 답 형식으로 답해 주시고, 생략한 번호는 추천값으로 진행합니다.
| # | 질문 | 추천값 | 이 답이 바꾸는 것 |
|---|---|---|---|
| 1 | … | … | … |
```

- 공통 질문 목록에서 1단계로 확정하지 못한 것만 고르고, 유형별 질문을 더한다.
- 질문은 보통 8~15개로 한다. 15개를 넘으면 결과를 덜 바꾸는 것부터 추천값으로 돌린다.
- 선택형으로 물을 수 있으면 선택지를 준다.

### 3단계 · 작업 명세서 (승인 1회)

```
[작업 명세서] 과업명 · v1 · 일자
- 목적: 받는 사람이 이 산출물로 할 다음 행동 1줄
- 산출물: 형식·분량·판형·파일명 규칙
- 기준 자산: 정본/템플릿/전회차 (경로)
- 입력: 원자료 경로와 판 번호
- 핵심과 우선순위: (사용자 답 그대로)
- 확정 사항(바꾸지 않음): 수치·문안·디자인
- 범위 밖: 하지 않을 것
- 완료 기준: 검증 항목과 통과 조건
- 기한: 외부 마감 / 내부 선행 기한 / 중간 보고 시점
- 처리 경로: 직접 또는 서브에이전트 N개 (사유)
- 가정: 추천값으로 정한 항목 목록
```

- 승인 신호(「진행」「OK」 등)를 받으면 실행한다. 수정 지시가 오면 명세서만 고쳐 다시 내지 않고 반영 즉시 실행한다.

### 4단계 · 무중단 실행

- 명세서 범위 안의 조사·작성·검증·수정은 묻지 않고 한다.
- 실행 중 생긴 의문은 「가정 대장」에 적고 합리적 기본값으로 진행한다.
- 같은 쪽이나 같은 산출물이 세 판을 넘기면 멈추고 원인을 보고한다(FB-185).

### 4.5단계 · 핸드오프 (작업 단위가 끝날 때마다)

claude.ai는 창을 닫는 순간을 Claude가 알 수 없다. 그래서 종료 때 한 번이 아니라 **작업 단위가 끝날 때마다** 새 핸드오프를 남긴다. 언제 창을 닫아도 이어받을 수 있게 하기 위해서다.

- **시점:** 산출물을 저장했을 때, 검증 한 판을 마쳤을 때, 사용자가 「마무리」「끝」「오늘은 여기까지」 등 종료 신호를 줬을 때.
- **위치:** Drive `/_핸드오프/`(폴더 ID `1HQOCwhpjFCMrQrZcx51esZPK_cAPys9m`).
- **파일명:** `HANDOFF_<키>_<업무>_YYYYMMDD_HHMM.md`.
  - 키: 프로젝트 지침의 「핸드오프 키: ○○」 값을 쓰고, 없으면 프로젝트 이름을 쓴다. 키에는 밑줄(_)을 넣지 않는다.
  - 업무: 제안서·조사설계·데이터검증·통계표·보고서·개별리포트·기타 중 하나. 한 프로젝트 안에서도 업무 갈래별로 이어받기 위해서다.
- **덮어쓰지 않는다.** 매번 새 파일을 만든다. 커넥터는 기존 파일을 고칠 수 없고, 이력도 남아야 한다.
- **양식:**

```
# HANDOFF · <키> · <업무> · YYYY-MM-DD HH:MM
- 목표: (이 과업이 끝나면 무엇이 나오는가)
- 입력 파일: 경로 · 판 번호
- 적용 규칙·표준: 이름 · 판 번호
- 완료한 것:
- 결과: 수치는 출처 파일과 함께
- 미해결·막힌 것:
- 다음 할 일: 새 창의 첫 동작 1줄
- 바꾸지 않을 결정:
```

- **새 창을 열었을 때:** 첫 실질 요청을 받으면 그 요청의 업무 구분을 먼저 정한다. `/_핸드오프/`에서 제목에 키가 든 파일 목록을 보고(제목만 조회), 같은 업무의 최신 파일만 연다.
  - 첫 줄에 「핸드오프: <파일명> 이어받음」을 적고 「다음 할 일」부터 시작한다.
  - 같은 업무 파일이 없으면 「이 업무 핸드오프 없음 — 새로 시작」이라고 적는다.
  - 업무 구분이 애매하면 업무별 최신 파일명을 한 줄씩 보여 주고 고르게 한다.
  - 다른 업무의 파일은 이번 요청이 그 결과를 입력으로 쓸 때만 연다. 예: 보고서 작업이 통계표의 최종 판을 쓰는 경우.

## 처리 경로 판정 — 단일 루프가 기본 (v1.1)

**기본은 단일 루프다:** 직접 작성 → 코드 검사기 → 수정. 서브에이전트를 여러 개 엮는 구조(역할 분리·병렬·감사 체인)는 아래 다섯 조건 중 **두 개 이상**일 때만 쓴다.

1. 독립 작업을 병렬로 펼쳤다가 하나로 모아야 한다(예: 시도별 같은 분석 17건).
2. 만든 주체와 검증 주체가 반드시 분리돼야 한다(예: 제출 직전 심사위원 채점 FB-164, 통계표 독립 검증 FB-08).
3. 단계마다 필요한 도구·권한·모델이 다르다.
4. 사람의 명시적 승인이 끼어야 한다(외부 제출·원본 삭제·비용).
5. 수 시간 이상 걸려 중간 저장과 재개가 필요하다.

**쓰지 않는 경우:**
- 단발성 작업
- 목표가 아직 모호한 탐색 — 먼저 착수 문답으로 좁힌다
- 기계로 판정되는 검사 — 검사기 스크립트로 한다
- 스크립트 하나로 되는 일

**판정 주체는 이 순서로 정한다:**
- 코드로 판정되면 검사기(문체 검사기·내검 엔진·합계 대조)가 판정한다.
- 매니저 결정 사항이면 사람이 판정한다(승인 지점).
- 둘 다 아닐 때만 모델이 판정한다.

**명세서 표기:** 작업 명세서의 「처리 경로」 칸에 `직접` 또는 `분업: 조건 ②④ 충족`처럼 근거 조건 번호를 적는다.

**비용 기준:** 직접 처리는 약 2만 토큰, 위임 1회는 약 25만 토큰, 판 하나 재작업은 약 100만 토큰이다(원장 §0-1). 문자열 치환·파일 하나 편집·대체 문안이 나온 수정은 직접 한다.

## 상태 인계 규격 (서브에이전트에 넘기고 돌려받을 때)

- **상태는 작업 명세서와 작업 폴더다.** 발주문에 내용을 요약해 옮기지 말고 파일 경로를 넘긴다. 요약은 인계 중 누락의 주된 원인이다.
- **원문 인용은 따옴표 텍스트로 넘기지 않는다.** `파일 경로 · 쪽/행 · 원문 그대로` 세 요소로 넘기고, 받는 쪽이 원문을 직접 연다.
- **회수 형식은 고정한다.** 결론 / 근거 위치(경로·쪽·행) / 바꾼 파일 목록 / 미해결 네 칸으로 받는다. 자유 서술로 받지 않는다.
- **감사·심사 지적은 검산한 뒤 다음 단계로 넘긴다.** 근거 위치를 직접 열어 확인한 뒤에 넘긴다. 2026-11-04에 심사위원 지적 3건을 검산 없이 집필 단계로 넘겼다가 셋 다 오진으로 판명된 사례가 있다(FB-56, FB-150).
- **되돌림 루프에는 상한을 둔다.** 같은 산출물이 세 판(FB-185), 감사가 다섯 판(FB-40)을 넘기면 멈추고 방식을 보고한다.
- **원장 조회:** `BACKLOG.md`는 FB 번호나 키워드로 해당 행만 뽑는다.
- **감사 범위:** 중간 감사는 고친 자리만 본다. 전수 감사는 제출 직전 1회로 한다.
