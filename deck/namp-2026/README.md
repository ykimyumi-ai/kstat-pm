# 2026 납품대금 연동제 실태조사 제안서 — 편집 가능 PPTX (발췌 17장)

원본 발췌본을 편집 가능한 PPTX로 재제작한 것이다.
1차 PDF 11장(1~11장), 2차 PNG 2장(12~13장), 3차 PNG 3장(14~16장),
4차 PNG 1장(17장)을 받아 처리했다.

## 왜 "변환"이 아니라 "재제작"인가

원본 PDF를 뜯어보면 자동 변환이 원천적으로 불가능하다.

| 검사 항목 | 결과 |
|---|---|
| 페이지 수 | 11 |
| 2차분 | PNG 2장(1536×1024) — 애초에 텍스트가 없는 이미지 |
| 텍스트 연산자(`Tj`/`TJ`) | **0건** — 텍스트 레이어가 없음 |
| 임베드 폰트 | 더미 `Helvetica` 1종(실제 미사용) |
| 페이지 구성 | 페이지당 이미지 XObject 1개 = 전면 래스터 이미지 |
| Producer | ReportLab (이미지를 PDF로 묶은 것) |

즉 원본은 "글자가 그려진 그림 11장"이다. PDF→PPTX 변환기를 돌리면 그림 11장이
붙은 PPT만 나온다. 그래서 모든 글자·도형·표를 네이티브 PPT 객체로 다시 그렸다.

## 산출물

```
out/2026_납품대금연동제_실태조사_제안서_발췌11p.pptx      # 1차 발췌 11장
out/2026_납품대금연동제_에너지경비_작동지표_2p.pptx        # 2차 발췌 2장
out/2026_납품대금연동제_업종별밀도_응답난이도_3p.pptx      # 3차 발췌 3장
out/2026_납품대금연동제_판별조사_2027승인연계_1p.pptx      # 4차 발췌 1장
out/2026_납품대금연동제_기대성과활용_투입체계_2p.pptx      # 5차 발췌 2장
out/2026_납품대금연동제_추가제안4종_1p.pptx                # 6차 발췌 1장
out/2026_납품대금연동제_적용대상탐색비용_1p.pptx            # 7차 발췌 1장
```

- **11.0 × 7.333 in**(원본 이미지 비율 3:2)
- 모든 텍스트가 편집 가능한 텍스트 박스 / 모든 도형이 네이티브 도형
- 10장 비목별 산출표는 `slide.addTable()` 네이티브 표 → 엑셀로 바로 붙여넣기 가능
- 폰트: `KoPub돋움체 Bold` / `KoPub돋움체 Medium` (kstat-ppt 표준)

수치나 문구가 바뀌면 **`content.js`만 고치면 된다.** 레이아웃 코드와 분리해 두었다.

## 웹 편집기 (사내망)

문구·수치를 브라우저에서 고치고 즉시 미리보며 PPTX 를 내려받는다. 팀원이 원문을
바꾸려고 매번 개발자를 거치지 않아도 된다.

```bash
npm install
npm run build:web      # web/bundle.js 생성 (소스를 고치면 다시 실행)
npm run serve          # http://localhost:8080
```

사내 서버에는 **Node 만 있으면 된다.** `web/bundle.js`·`web/vendor`·`web/fonts` 를
저장소에 함께 두었으므로 `npm install` 없이 `node web/server.js` 만으로 뜬다.
(`verify.py` 를 웹에서 돌리려면 python3 와 python-pptx 가 추가로 필요하고, 없으면
검증 버튼만 비활성으로 알려 준다.)

서버를 띄우기 어려운 자리(메신저로 보내 보여 주기 등)에는 **단일 파일 데모**를 쓴다.

```bash
npm run demo           # web/demo.html — 파일 하나(6MB), 더블클릭하면 열린다
```

폰트·이미지·번들·원문을 전부 안에 담아 서버 없이 돈다. 편집기와 **같은 코드**라
미리보기와 PPTX 다운로드가 실물과 똑같고, 서버가 없어 저장·검증만 막아 둔다.
생성물이라 저장소에는 넣지 않는다(`.gitignore`).

### 어떻게 CLI 와 같은 파일이 나오는가

PPTX 를 브라우저에서 만든다. 슬라이드 레이아웃 코드(`slides/*.js`)와
`helpers`·`theme` 는 한 줄도 고치지 않고 그대로 쓴다. 브라우저와 노드가 갈리는
지점은 셋뿐이라 `web/deck.js` 가 전부 흡수한다.

| 갈리는 지점 | 처리 |
|---|---|
| 폰트 폭 | TTF(3.1MB) 대신 `tools/gen-metrics.js` 가 뽑은 표(48KB) 주입 |
| assets 경로 | `helpers.setAssetBase()` 로 파일 경로 → URL |
| pptxgenjs | 벤더가 제공하는 브라우저 번들(`web/vendor/`) |

정말 같은지는 추측하지 않고 **실제 Chromium 을 띄워 확인한다.**

```bash
npm i --no-save playwright-core
npm run parity         # 웹 산출물과 CLI 산출물의 슬라이드 XML·미디어를 바이트 비교
```

슬라이드 XML 에는 시각·UUID 가 없어(생성 시각은 `docProps/core.xml` 에만 있다)
바이트 비교가 가능하다. 7개 프리셋 전부 일치해야 통과다.

### 미리보기

`slides/*.js` 는 `sl.addShape/addText/addImage/addTable` 과 `pres.shapes.*` 만 쓴다.
그래서 같은 모양의 가짜 `pres`/`sl`(`web/svgpres.js`)을 넘기면 **레이아웃 코드를
고치지 않고** SVG 를 뽑을 수 있다. 21장 2,666개 도형·글자를 70ms 남짓에 그린다.

줄바꿈은 `fontmetrics.wrapLines` 를 그대로 쓴다. 브라우저가 알아서 접게 두면 화면과
PPTX 가 갈리므로, "PowerPoint 가 실제로 하는 일"이 아니라 **"빌더가 가정한 모델"**을
보여 준다. 그래야 아래 넘침 경고를 믿을 수 있다.

> 미리보기는 PowerPoint 렌더가 아니다. 배치·줄바꿈 확인용이며, 최종 확인은 실제
> PowerPoint 에서 한 번 여는 것을 권한다.

### 넘침 경고

이 프로젝트에서 가장 자주 터진 문제가 "10pt 하한 때문에 문구가 칸을 넘거나 줄이
늘어나는 것"이다. `helpers.fit`/`fitBox` 는 10pt 까지 줄이다 조용히 포기하므로
편집자가 알 방법이 없었다. 편집기는 글자를 고칠 때마다 같은 계산을 돌려
**칸에 들어가는 줄 수를 넘긴 텍스트**를 표시한다.

판정은 높이가 아니라 줄 수로 한다 — 배지·따옴표처럼 작은 상자는 담는 그릇이 아니라
위치 기준점이라 한 줄은 넘쳐도 정상이기 때문이다. 지금 덱의 기준선은 **7건**이고,
그중 6건은 10pt 하한에서 빌더가 실제로 포기한 자리다(아래 "원본과 다른 점" 참조).
편집기는 기준선을 기억해 **내 편집이 새로 만든 경고만** 부각한다.

### 안전장치

- **항목 추가·삭제는 막는다.** 슬라이드 21장이 전부 `forEach((x, i) => ...)` 로
  좌표 배열을 인덱스로 참조하므로, 배열 원소가 하나만 늘어도 좌표 배열 밖을 참조해
  레이아웃이 조용히 깨진다. 편집기는 글자만 고치게 하고, 서버도 저장 직전에 골격
  (배열 길이·키 구성)이 같은지 확인해 다르면 **422** 로 거부한다.
- **동시 편집**: 저장은 읽어 온 버전을 함께 보내고, 그 사이 누가 먼저 저장했으면
  **409** 로 막는다. 저장 전 원본은 `web/.history/` 에 남는다.
- **번들 최신성**: 소스를 고치고 `build:web` 을 잊으면 서버가 뜨지 않고 알려 준다.

### 원문의 단일 소스

원문·수치는 `content.json` 한 곳에 있고 `content.js` 는 로더다. CLI 도 웹도 같은
파일을 본다. 편집기가 저장하면 CLI 로 그대로 다시 만들 수 있다.

```bash
npm run build:all && npm run verify -- out/<파일> --ids s20
```

## 검증

```bash
python3 verify.py out/…발췌11p.pptx --ids s01,s02,s03,s04,s05,s06,s07,s08,s09,s10,s11
python3 verify.py out/…작동지표_2p.pptx --ids s12,s13
python3 verify.py out/…응답난이도_3p.pptx --ids s14,s15,s16
python3 verify.py out/…2027승인연계_1p.pptx --ids s17
bash tools/render.sh  # PPTX → PDF → 장별 PNG (눈으로 원본과 대조)
```

`verify.py`가 확인하는 것:

- 대상 슬라이드 수 / 규격 11.0×7.333in
- 슬라이드당 도형 20개 이상 (kstat-ppt 원칙 17 도형 밀도)
- 금지 요소 0건: `roundRect` 도형, `shadow`, 8자리 hex
- 폰트 크기 전량 10pt 이상 (kstat-ppt 원칙 15)
- 네이티브 표 존재(10장이 대상일 때) / 삽입 이미지 개수(14~16장이 대상일 때)
- **`content.js`의 모든 문자열이 PPTX 안에 실제로 들어갔는지 전수 대조**

현재 상태: 네 파일 모두 전 항목 통과 / 원문 누락 0건.

| `assets/*.png` | 14~17장 사진·아이콘(원본 크롭). 재생성에 필요 |

| `tools/extract-assets.py` | 원본에서 사진·아이콘을 잘라 `assets/` 로 저장 |

## 설계 메모

**좌표는 눈대중이 아니라 실측이다.** 원본 이미지에서 색상 경계를 스캔해 도형의
픽셀 좌표를 뽑고(`tools/measure.py`), 그 값을 그대로 코드에 쓴 뒤 `theme.js`가
인치로 환산한다. 슬라이드 코드의 숫자는 전부 원본 픽셀 좌표다.

**글자 크기도 실측 기반이다.** 원본에서 잰 한글 잉크 높이(px)를 `s.FS()`가 pt로
바꾼다. 계수 0.99는 원본의 제목·부제·인용문·각주 4개 표본에 대해 KoPub 실제
메트릭으로 계산한 폭이 원본 폭의 0.98~1.04배가 되도록 맞춘 값이다.

**넘침은 계산으로 막는다.** `fontmetrics.js`가 KoPub TTF의 advance width를 직접
읽어 문자열 폭을 계산하고, 렌더러가 한글↔서양문자 경계에 넣는 약 0.25em 간격까지
반영한다. 이 값으로 폰트를 자동 축소해(최소 10pt) 박스를 벗어나지 않게 한다.

**pill(양끝 둥근 라벨)은 도형 합성이다.** kstat-ppt가 `ROUNDED_RECTANGLE`을
금지하므로(PPT 손상) 모서리 원 4개 + 사각형 2개로 합성했다. 14~16장의 둥근 패널·
카드도 같은 방식(`roundRect`)으로 그린다 — 사진 크롭이 원본의 둥근 모서리를 품고
있어 각진 사각형으로 그리면 이음매가 드러나기 때문이다.

**14~16장의 사진은 원본 크롭을 삽입한다.** 공장·크레인·서버·트럭·클립보드 사진과
하단 원형 아이콘은 도형으로 다시 그릴 수 없어 `tools/extract-assets.py` 로 원본에서
잘라 `assets/` 에 두고 그 자리에 얹었다. **글자와 도형은 전부 네이티브이므로 편집
가능성은 그대로다.** 사진이 pill 위로 걸친 곳은 pill 을 먼저 그린 뒤 크롭을 얹고,
pill 색으로 팔레트값이 아니라 원본 실측색(`002677`·`9A835C`·`012984`)을 써서
이음매를 없앴다.

## 원본과 다른 점 (의도된 차이)

1. **7·8·9·11장은 원본이 A4 가로 비율(1.414)**이다. 확정 규격인 3:2(1.5)로 옮기면
   세로 여유가 약 6% 줄어, 이 4장은 행 간격·패딩이 비례로 좁아졌다. 글자는 그대로다.
2. **원본의 초소형 주석은 10pt 미만**이지만 kstat-ppt 원칙 15(최소 10pt)에 따라
   10pt로 올렸다. 그래서 1장 우측 골드 배지, 2장 판별조사팀 주석 등 몇 곳은
   원본보다 배지가 넓거나 두 줄이 된다.
3. **3장 단계 카드**는 원본(357~628px)보다 7px 아래로 늘렸다. 원본 본문이 10pt
   미만이라 최소 10pt를 지키면서 같은 내용을 담으려면 그만큼 여유가 필요했다.
4. **10장 비목별 산출표**의 열 너비는 원본(197/500/175px)이 아니라 230/442/200px로
   다시 나눴다. KoPub이 원본 서체보다 넓어 비목명·금액이 접히는 것을 막기 위해서다.
5. 페이지마다 상단 라벨·번호 체계가 제각각인 것(4장 "8.", 10장 "2.", 11장 "5.")은
   **원본 그대로 유지**했다. 발췌본이라 원 덱의 번호 체계를 임의로 고치지 않았다.
6. **12장 ① 본문 첫 줄**(`원가구조를 재료비…4구분으로 기재`)은 10pt에서 494px가
   필요한데 원본 본문 열은 436px이라 두 줄이 된다. 열을 넓히면 옆의 `설계 근거`
   열이 밀려 더 큰 왜곡이 생겨, 두 줄을 택했다.
7. **13장 좌 패널**은 원본(18~926px)보다 18px 넓다. 10pt 하한에서 ③ 회피율·②
   이행률 산식이 각각 468·430px를 요구해 원본 폭으로는 산식이 두 줄로 접힌다.
8. **13장 하단 ② 공표 단위**는 원본 3줄이 4줄이 된다. 옆 열의 악센트 바와
   부딪히지 않는 선에서 최대로 넓힌 결과다.
9. **14~16장은 원본이 A4 가로 비율(~1491×1055)**이라 3:2로 옮기며 세로가 약 6%
   압축된다(7·8·9·11장과 같은 처리).
10. **사진 해상도는 원본 크롭 그대로**다. 원본이 슬라이드 폭 1491~1536px 기준이라
   확대 인쇄 시 다소 거칠 수 있다. 원본 사진 파일이 있으면 `assets/` 의 같은
   이름으로 바꿔 넣으면 그대로 반영된다.
11. **17장 우측 패널의 첫·셋째 항목**은 원본 1줄이 2줄이 된다. 오른쪽에 사진이
   있어 글 폭이 559px뿐인데 10pt 하한에서 584px가 필요하기 때문이다.
12. **17장 타임라인 노드는 글자 크기가 제각각**이다(잉크 22~41px). 원본 실측값을
   노드별로 `content.js` 의 `ink1`·`ink2`·`inkU` 에 담아 그대로 재현했다 —
   균일하게 적용하면 06·07번 노드 글자가 겹친다.
13. **18장 02행 '3영업일 … 7영업일'** 은 원본에서 한 줄이지만 두 줄이 된다. 작은
   글자가 10pt 하한으로 올라가 줄 폭이 310px에서 모자라기 때문이다. 아래 03행을
   침범하지 않도록 큰 숫자도 원본(잉크 28px)보다 줄였다.
14. **18장 좌 패널 불릿**은 원본 2줄이 3줄이 되는 칸이 있다. 원본이 9.4pt 상당이라
   10pt 하한에서 6~7% 넓어진다. 원본이 비워 둔 아래 여백까지 블록을 늘려
   구분선을 넘지 않게 했다(세로 규칙선도 같은 길이로 늘렸다).
15. **19장 조직도의 칸 너비·행 구분선 위치는 원본 고정값이 아니다.** 원본의 업무
   설명은 7.7pt 상당인데 10pt 하한에서는 4열(이름·역할·업무·기간)이 패널 폭
   359~381px에 들어가지 않는다. 그래서 `slides/s19.js` 의 `layout()` 이 실제 폰트
   메트릭으로 행별 필요 줄 수를 계산해 칸 너비와 구분선을 배분한다. 결과적으로
   구분선 y가 원본과 최대 30px 다르고, 업무 설명이 원본보다 한 줄 더 접힌다.
16. **19장 그룹 패널은 원본(518~844px)보다 위로 6px·아래로 16px 넓다.** 위 항목의
   계산으로도 세로가 22px 모자랐다. pill 도 같은 만큼 올렸고, 하단 밴드(874px)와는
   겹치지 않는다.
17. **20장 상단 3단 띠**는 조각마다 글자 크기가 달라(꼬리 문구가 더 크다) 기존
   `fit` 을 쓸 수 없다. 조각별 실제 폰트 폭을 더해 한 줄에 들어가는 크기를 직접
   찾는다. 그래도 둘째 띠는 KoPub 기준 473px 칸에 436px로 겨우 들어가므로,
   다른 서체로 바꾸면 두 줄이 될 수 있다.
18. **21장만 원본이 이미지가 아니라 PDF**다(한글 1.3 출력, A4 가로 841×595pt).
   다만 텍스트 레이어가 없어 결국 래스터를 실측했다. 내부 이미지가 1404px 폭이라
   120dpi 가 원본 해상도지만, JPEG 가 물러 경계 검출이 흔들려 **300dpi(3505×2480)**
   로 뽑아 실측했다. 그래서 이 장만 좌표 단위가 다른 장의 약 2.3배다.
19. **21장은 A4 가로 비율(1.413)**이라 3:2 로 옮기며 세로가 약 6% 압축된다
   (7·8·9·11·14·15·16장과 같은 처리).
20. **21장 좌 패널의 수치 블록은 y 를 블록마다 따로 준다.** 줄 수가 1~3줄로 달라
   균일 배치하면 '88,000개사'와 '접촉 필요'가 겹친다. 원본 실측 y 를 그대로 쓴다.

## 렌더 검증의 한계

`tools/render.sh`는 LibreOffice로 렌더한다. 컨테이너에 KoPub돋움체를 설치해 두면
실제 폰트로 검증되지만, LibreOffice와 PowerPoint는 자간·줄바꿈 규칙이 미세하게
다르다. 배치 어긋남·겹침·잘림은 이 검증으로 잡히며, 마지막 확인은 실제 PowerPoint에서
한 번 열어보는 것이 좋다.
